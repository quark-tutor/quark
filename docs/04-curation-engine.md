# Curation engine

The engine follows a multi-year plan, not a random stream. It runs every week on its own, and a guardian taps once to make the week live.

## The long-term plan

The backbone is a knowledge sequence such as the [Core Knowledge Sequence](https://www.coreknowledge.org), organized as a timeline of history. Each theme ties several subjects together. For example, an Ancient Egypt week might include:

- the Nile and the pyramids on the map
- Egyptian art on the wall
- simple machines and levers in science
- hieroglyphs as a puzzle
- Greek and Egyptian myths in the car

Tying the subjects together is what makes knowledge stick.

## The weekly cycle

1. Read last week's activity and the results of delayed checks (see [Teaching that tests itself](12-teaching-that-tests-itself.md)), the questions kids asked and any notes from parents.
2. Choose next week's theme from the plan, adjusted for what caught each child's interest.
3. Pull material only from trusted, free, public-domain or museum sources (see [Resources](05-resources.md)).
4. Write explanations at each child's level, through the [lenses](17-lenses.md) that open the theme for that child. For example, one version for a 7-year-old who likes building things and another for a 9-year-old who likes stories. The lens changes the way in, never the facts.
5. Load the touch points, queue the audio and send the parent digest.

## Per-child profile (draft)

- Age and reading level
- Current interests (sharks, knights, space, Minecraft and so on)
- Topics explored and how deep they went
- Questions asked
- Parent notes ("go deeper on this", "skip that for now")

## How the approval rule is built

Everything a child sees comes from `content_items` with `approved = true`. `npm run content:fetch` fills that table from the sources the imported plan names, and `/parent/content` is where a guardian decides the rest.

- **Sources and adapters.** `content_sources` has four rows, each with its rule in `license_note`: the Met (CC0 when `isPublicDomain`), the Art Institute of Chicago (CC0 when `is_public_domain`, images through IIIF at 843 pixels), Wikimedia Commons (the license read from each file's own page) and Musopen (checked by hand, never approved automatically, because its site refuses automated requests). Each has one adapter under `core/content/` that fetches one item by its id with plain `fetch`. There is no search: the plan names exact items.
- **Flags.** The gate model looks at each item's image and what its source says about it (`core/prompts/flag-content.md`) and returns flags from a fixed list: `nudity`, `violence`, `frightening` and `needs_review`, with one sentence for parents. Frightening is judged for a 7-year-old: a mummy's face can pass, a flayed figure can't.
- **The rule.** An item is approved automatically only when its license is CC0 or public domain and it has no flags (`core/content/rule.ts`). `approved_how` records `auto` or `guardian`. Everything else stays unapproved and waits. A guardian's rejection is kept in `rejected_at` and `rejected_by`, and a rejected item is never approved again.
- **The stored copy.** Every approved or waiting image is copied into the private Storage bucket `content` at `<source>/<external_id>.<ext>`, recorded in `metadata.storage_path` beside the original URL, because the wall works offline and never loads images from museum sites. An original over 20 MB (Storage takes at most 50 MB a file, and a 30,000-pixel scan is no use on an iPad) is stored as the source's large preview instead, 1280 pixels wide for Commons, and `metadata.stored_from` says `preview`. The Art Institute's image server wants the same `AIC-User-Agent` header as its API. Recordings keep their URL only, for now.
- **Running it again** changes nothing: an item already in the table isn't fetched, flagged or copied again. A failed fetch stops the run and names the item.
- **The review page.** `/parent/content` lists the items waiting, then the approved ones, then the rejected ones, each with its picture, source, license, flags and the model's note. Any guardian can approve or reject; both are written to the audit log.

## How a topic gets its picture

Every topic in a stretch names one or two items in its `sources`, so that no card comes out text only and a topic can look different when it comes back later in the week. The adapters fetch by exact id and never search, so finding the items is a separate step that a person signs off on.

- **Finding candidates.** For each topic without sources, Claude Code searches the Met (Collection API search), the Art Institute of Chicago (API search, public domain only) and Wikimedia Commons (file search), using throwaway code that isn't kept and isn't added to the adapters. Every candidate is then fetched through the real adapter, so its id and license are the ones `content:fetch` will see.
- **The rules for a candidate.** CC0 or public domain only; for Commons, the license on the file's own page. No nudity. Nothing frightening for a 7-year-old: a mummy's face can pass, a flayed figure can't. A real object or place that shows the topic's mechanism (a nilometer for the flood, a sledge for hauling, a weight carved with number signs for the puzzle) before a modern illustration. A "listen" topic gets a recording, preferably from Commons, because Musopen is checked by hand and never approved automatically.
- **The candidates file.** `plan/candidates/<stretch>.md` has one section per topic (week, slot, title) with 2-4 candidates: source, id, title, URL, license, what it shows and why it fits, with the one or two Claude Code would take marked. It's committed before anything changes, and a guardian picks. The chosen items go into the stretch's `sources` and each topic's `sources`. The file stays as the record of why each was picked.
- **The validator warning.** `planWarnings()` in `lib/plan.ts` names every topic without sources, and `plan:import` prints them. It's a warning, not an error, so a stretch can be imported while its pictures are still being found. A test holds the Egypt stretch to none.
- **When a topic has no good item.** The candidates file says so plainly, naming what was looked for and not found (for Egypt: a photo of a nilometer's scale marks, a knotted 3-4-5 rope, papyrus being made, a recording of a ney). If one of a topic's items fits, the rest of the topic stays text only. If none fits, the topic stays text only, the warning keeps it visible, and the week report and `/parent/week` name the gap. Anything better done by hand than shown goes to [open questions](08-open-questions.md) as a possible parent activity.
- **After picking.** `plan:import`, then `content:fetch`, which flags and approves as above. Anything flagged waits at `/parent/content` for a guardian. The first run, on 15 Oct 2026, added 33 items for Egypt: all passed automatically, with no flags.
- **Layer 1 always has one** (decided 15 Oct 2026). Layer 1 is the card a child meets first, so when a day-slot's topic has an approved item, layer 1 of its idea chain must use one; layers 2-4 may go text only. The ideas prompt says so, and `firstLayerProblem()` in `core/curation/ideas.ts` checks it the way the hint check works. A chain whose layer 1 has no item (or an id that wasn't offered) is sent back once with the problem named. If it still has none, the chain is kept, and the `week:build` report lists it under "first cards without a picture" with the number of chains sent back. The first day 1 rebuild after this (15 Oct 2026) needed no second asks: all five first cards had an item, and the six text-only layers per child were all in layers 2-4.
- **A topic whose only item can't show its first idea.** Week 1's listen topic had only the Aida recording, so "instruments from paintings and tombs" had nothing to show. A Met harp (`met-arched-harp`) and a bronze sistrum (`met-bronze-sistrum`) were added beside it, picked the same way as the rest.

## How a week is built

`npm run week:build -- --week 1` turns the family's week 1 of the plan, mixed as below, into a theme, its shared ideas, and every child's cards and questions. The theme is `generating` while it runs and `review` when it's done; nothing goes live here, and every card is written with policy `pending`; the gate then checks each one (below, "How the gate is built"). A week already built is refused unless `--rebuild` is given, which deletes that week's ideas, cards and questions first (or, with `--child`, only that child's cards). `--days` builds fewer days, for a cheap trial. The run ends with a report: ideas and cards per child, the lenses used, cards without a picture, slots with no approved item, and the tokens and cost per model. `/parent/week/<theme>` shows the result, read-only, with each card's verdict from the gate: each card's picture (tap to open it large, from a signed URL to the private copy) or recording (a player that never autoplays; for Commons sound files the MP3 copy Wikimedia keeps, which iPad Safari plays), with its title, creator, date, source, license and credit line, and, where a topic has no approved item, a note naming the plan topic so the gap can be filled.

- **Units.** A theme is one week. A day is five cards, one per slot: look, wonder, listen, then, puzzle. An idea is one fact or concept, anchored to a plan topic and, where one is approved, a content item, with its question and answer key; ideas are shared by every child. A card is one child's rendering of an idea, at that child's level, through a lens. Layers 1-4 are separate cards on the same idea, each a step deeper, linked by `parent_idea_id` and `parent_card_id`.
- **Ideas** (`core/curation/ideas.ts`, `core/prompts/ideas.md`, on `QUARK_MODEL_CURATE`). One call per day and slot returns a chain of four layers on that day-slot's topic (a thread topic or a short lesson): title, statement (the fact in plain words, mechanism named), question, acceptable answers with a one-line rubric, and which approved content item it uses, if any. The call says whether the topic is part of the thread (with its chapter and the thread's last six topics, to build on) or a short lesson, which has to make a whole in four layers, and passes on any parent's part ("play the first movement for him"), with its topic's own perspective and values points. Layers 1-2 draw on the 2-3 summary and layers 3-4 may add the 4-5 material, since both children share the chain. Only approved items are offered; a slot whose topic has none is text only, and the report lists it. `source_refs` holds the plan topic keys and the item with its attribution.
- **Lenses** (`lib/lenses.ts`). A pure function picks a lens per day-slot for each child; see [Lenses](17-lenses.md), "How the picker works".
- **Cards** (`core/curation/cards.ts`, `core/prompts/card.md` behind `manner.md`, on `QUARK_MODEL_WRITE`). One call per child per day-slot renders the four layers as cards: title, text, image_alt, read_aloud, question, hints and handoff. The prompt carries the idea chain, the lens and its question, the child's nickname, age and reading level and nothing else about the child (rule 7), the family's own words (`values_profiles.statement`), the topic's own perspective and values points, and any parent's part, which the first card's handoff asks the child to get a parent for (never naming an app, a website or a link), so a card is written right the first time rather than fixed by the gate. An interest may open the first card on at most a quarter of the week's day-slots (`cards.door`), and never changes what is taught. Science cards pair how it works with who it helps. `cards.level` records the reading level and age written for.
- **Checks, in code.** Each card is checked before it's saved: four cards, two or three hints, a handoff, a description when there's a picture, the whole card in read_aloud for a child who is read to, no brilliance words, no links, and no hint that gives the answer away (every meaningful word of an accepted answer appearing in a hint counts). A failed check sends the call back once with the problems named. A card still failing after that is saved as `blocked` with the reason in `policy_notes`, and is never shown.
- **Questions.** One `questions` row per card: the card's question, the idea's answer key, and the hints in order. The handoff ("Ask Dad what a dam does to a river") stays on the card, not among the hints. `difficulty` is left empty until phase 6.
- **Models and cost** (decided 14 Oct 2026). Ideas run on the strongest model because they carry the facts and are shared; cards run on a cheaper one because they are many and are mostly writing. At Claude Opus 5.5 for ideas and Claude Sonnet 5.5 for cards, a seven-day week for two children is about 35 idea calls and 70 card calls, estimated at about $5.70.

## How a week is mixed

Decided 16 Oct 2026 (docs/08, "The plan: short lessons and child-chosen depth" and "Mixed weeks"): a week is a mix. One slot a day carries the running thread, a stretch such as Ancient Egypt, and the other four carry short lessons, each one idea chain on one slot, not tied to a stretch or a week. Both children get the same short lessons, and each card is still written at the child's own level and through the child's own lens.

- **The library.** `plan/short-lessons.yaml` holds the short lessons in the order they run: a key that is never reused, a subject (the same seven as stretches), a slot, a title, a summary per grade band in the stretch style, one or two sources (CC0 or public domain, picked like a stretch's; the candidates and the reasons are in `plan/candidates/short-lessons.md`), its values points (required, `[]` for none, so the gate in step 5 can read every lesson's answer) with a perspective when there are any, and an optional parent note. `validateLibrary()` in `lib/plan.ts` checks it, and `libraryWarnings()` names lessons without sources. Any subject may sit on any slot (the slot is what the child does); whale calls are science on the listen card.
- **The rows.** `plan:import` writes each lesson as two `plan_topics` rows, `short/<key>/2-3` and `short/<key>/4-5`, with `kind` `short`, no week and no parent, and `position` its place in the library. A stretch's chapter rows are `kind` `week` and its topics `kind` `thread`, with `position` counting through the whole stretch (Egypt 1-24). Stretch keys didn't change. Migration `20261016000001_mixed_weeks`.
- **The schedule.** `weekSchedule()` in `core/curation/schedule.ts` is pure. Day d of the family's week N takes the thread's topic 7(N-1)+d on the slot it was written for, so the thread moves through the slots: Egypt's order is then, wonder, look, listen, then, puzzle in every chapter, and its first week has the thread on then, wonder, look, listen, then, puzzle, then. Each other slot takes the next short lesson written for it that no earlier week used (a theme with a lower `themes.plan_week`); a rebuild keeps the week's own lessons first, so adding to the library changes only weeks not yet built. The whole week is scheduled even when `--days` builds fewer, and if any slot runs out the build stops before spending anything and names the slots. When the thread has run out (Egypt fills weeks 1-3 and three days of week 4), all five slots take short lessons until Brandon and June pick the next thread. Week 1 uses exactly the 28 lessons in the library.
- **The theme.** Found by `themes.plan_week` (unique per family), titled from the thread's chapter on its first day ("Week 1: The river, with short lessons"), with `topic_ids` listing every row the week uses, both bands, and the chapter rows. A rebuild gives an existing theme this run's title and topics, which is how the day 1 built on 15 Oct became a mixed week.
- **Values points per topic.** A thread topic carries its chapter's perspective and values points (Egypt week 3's points ride on its topics); a short lesson carries its own. The ideas and card prompts take them per chain, not per week.
- **Music Quark can't hold** (decided 16 Oct 2026). When no open recording exists, the lesson keeps a picture (Beethoven's handwritten first page for four-notes), its summary says a parent plays it, and its parent note says what to play. The ideas are written for listening with a parent, and the first card's handoff asks the child to get a parent for it. The kid view never links to the music and Quark never copies it in (rule 4).
- **The report.** `week:build` prints, before it spends anything, which slot carries the thread each day and which short lessons run, then the usual report.

The first mixed build, day 1 of week 1 on 16 Oct 2026, put Egypt on the then card (The Nile, from source to sea) beside great-wave, leap-years, carnival-of-the-animals and two-dice. Every first card had a picture or recording, with no chain sent back; 11 of 20 layers used an item for each child. It cost $0.85. The 7-year-old's two-dice layer 1 was held back by the hint check, a false positive (see docs/08).

## How the gate is built

Built 20 Oct 2026, phase 3 step 5 (`docs/gate-slice.md`; the decisions are in docs/08, "The policy gate"). Rule 5: a card leaves `pending` only through the gate, to `passed` or `blocked`. Nothing else in the code sets `passed`, and the gate never rewrites a card, so `rewritten` stays unused: a card it holds back is rebuilt (`week:build --rebuild --child`) or left out.

- **When it runs.** At the end of `week:build`, once every card is saved, and on its own as `npm run gate -- --week N [--child X]` (and `gate:live`, not run yet). Both call `runGate()` in `core/curation/gate.ts`, which is pure: the database and the model are passed in, as in `buildWeek`. A card the card checks held back is left alone; a card with a verdict on today's rulebook and floor is skipped; every other card is checked once, including one checked against an older rulebook. `week:build` checks that `QUARK_MODEL_GATE` is set before it spends anything, and lists, before spending, what the family's settings decide for each child's slots; with `--plan` it stops there, having spent and written nothing.
- **The family's settings come from the merge.** `lib/family-rulebook.ts` holds `loadFamilyInputs()`, `merge()` and `familyRulebook()`, the functions the compare page calls and the rulebook is saved from (moved unchanged from `lib/family-save.ts`), so the gate has no rule of its own about what the guardians' answers mean. If the family has no rulebook, or the saved `source_hash` is not the hash of the answers now, the gate checks nothing, every card stays `pending`, and the command exits with an error.
- **Rules in code first.** For each subject a card's topic marks: any one guardian's blackball, or "Don't bring it up", holds back the topic's cards for every child; "Not yet" holds them back for a child younger than the age set for that child. The reason names the subject and never the guardian ("Subject 5 (Age of the Earth and universe) is blocked by a guardian."). A subject not settled yet (one guardian has answered, or they differ) is not held back in code: it goes to the model as parent-led. Coarse on purpose: a topic that touches a never subject holds back all four layers.
- **Then one model call per card**, on `QUARK_MODEL_GATE` (Opus 5.5), with `core/prompts/gate.md` and then `gate/safety-floor.md` as the system prompt. The call carries the rulebook copy that names no child (`renderPolicy(..., { forGate: true })`: the "Not yet" lines without nicknames, since code has applied the ages, and no speak-first paragraph, which is about the live tutor); the topic's subjects, each with its perspective and the family's setting; the child's grade band (2-3 for 8 and under, 4-5 for 9 and over); the `careful_about` note when the parents wrote one; and the card as the child would see it (title, text, read_aloud, question, hints, handoff, image_alt). Nothing else about the child: no nickname field, exact age, birth month, sex, reading level, interests, lens, door or `cards.level` (rule 7; a test holds it). A card's own words may carry the nickname, because the writer used it; that is left as written.
- **The verdict.** JSON: `pass` or `block`; reasons, each a rule (`parent_led`, `perspective`, `blocked_topic`, `rule_1`, `rule_6`, `frightening`, `caution`), a subject number and one sentence for parents; and up to two reader notes, the card read as an experienced teacher would, which never change the verdict. A handoff that names a parent is by design and is never a note (`gate.md` v2). A block with no reasons, a pass with reasons, a refusal or a reply that doesn't parse leaves the card `pending`. A caution reason that repeats four words in a row of the parents' note is replaced with a sentence code writes, so the note is never quoted back.
- **What is stored.** `cards.policy_notes.gate`, beside the card checks' `validation`: `{ by: "code" | "model", rulebook: <source_hash>, floor, floor_first_guess, model?, reasons, reader?, checked_at }`. The rulebook's hash is read again before each verdict is written; if it changed during the run, no more verdicts are written, the rest stay `pending`, and the command exits with an error.
- **Fail closed.** A model error, a refusal or an unreadable reply leaves the card `pending`, and anything left pending ends the run with an error; a card is never `passed` by default. The report counts one fault once, without each reply's request id.
- **The safety floor**, `gate/safety-floor.md` v1: docs/09's three items (body safety, how to tell a trusted adult, emergency basics), always taught at an age-appropriate level, marked "A first guess, pending June" until June has read it and a commit removes the line. The gate reads it ahead of the family's rulebook: a card on the floor is never held back by a blackball or by a never or parent-led setting, only by rule 1 or 6. Each verdict records the floor's version and whether it was still a first guess. It changes by commit only; no screen changes it.
- **The report and the page.** `week:build` and `gate` print passed, held back in code, held back by the checker, left pending and why, the reasons by rule, the reader notes, and the gate's tokens and cost per card; `gate` on its own writes a `model_runs` row of kind `gate`. `/parent/week/<theme>` opens with the counts and the floor's version, and each card says "Held back by the card checks", "Held back by your rulebook, before any checker read it", "Held back by the checker", "A teacher's eye" for a reader note, or "Checked against an older rulebook". It never says which guardian blocked a subject.
- **The card writer** is told how the family wants its children to learn to act, in the rulebook's own words (`learnsSentence()` in `lib/policy.ts`; `card.md` v5). It still does not get `careful_about`, and a test holds that.
- **Cost, measured on test (20 Oct 2026).** $0.026 a card the model reads: about 4,600 tokens in and 360 out a call on a one-guardian Quick-start rulebook (about 6,500 characters in the gate's copy). That is half the step 1 estimate, because the gate thinks little (about 250 thinking tokens a call, against about 2,270 on a card call). Day 1 with the gate cost $1.66 (ideas $0.20, cards $0.68, the gate $0.77). A full week is about $11.55 as `estimate()` prices it, or $13.44 if all 280 cards reach the model; the run line is $25 (docs/08). The live rulebook carries both parents' notes and own words, so it is longer; measured on live below.
- **Cost, measured on live (20 Oct 2026).** `gate:live` on week 1: 40 cards, 39 read by the model, **$0.93 in all, $0.024 a card** (about 4,670 tokens in and 257 out a call). The live rulebook is **6,823 characters** in the gate's copy, only about 5% longer than the test one, so the cost per card is no higher and the week estimate above stands. Result: 39 passed, 0 held back in code, 0 by the checker, 0 pending; 1 card was left as the card checks held it.
- **`gate.md` v2 on its first real run (live, 20 Oct 2026).** 36 of the 39 cards drew a reader note, and none was about a handoff naming a parent, so the v2 line held. One run is a small sample. About half the notes say the card's text gives the answer just before the question; that is the card prompt's to fix (step 4d), not the gate's.

Proven on `quark-test`, 20 Oct 2026, on day 1 with how-fossils-form (subject 5) and doubling-grains (subject 24) moved onto it for the test: 28 cards passed, 8 were held back in code by a blackball on subject 5, 2 by the checker (a Great Wave layer for the caution note, a bank-interest layer as parent-led) and none were left pending. With the blackball lifted, the hash changed and a re-check of every card ($0.99) sent the fossils cards to the model, which passed layers 1, 2 and 4 and held back layer 3 as parent-led. A run with a model name that doesn't exist left all 38 cards `pending`, exited with an error and spent nothing. The twenty-question test run is described in `gate/values-interview.md`.

## How the models and costs page is built

`/parent/models` shows what Quark spends on language models and on which ones, so a guardian doesn't need a terminal to find out. It is read-only (decided 16 Oct 2026), any guardian can open it, and it is linked from `/parent`. Nothing on it reaches the kid view.

- **Which model does which job.** Ideas (`QUARK_MODEL_CURATE`), cards (`QUARK_MODEL_WRITE`), and the gate and content flags (`QUARK_MODEL_GATE`), read from the environment where the page runs, with each one's price. A variable that isn't set says so. Locally that is `.env.local`; on Vercel the same names are set in the project's environment.
- **Prices.** The table in `core/prices.ts` (Anthropic's list prices, dollars per million tokens, input and output), with `PRICES_CHECKED`, the date they were last checked against Anthropic's list (16 Oct 2026). Whoever checks them again moves the date.
- **Every run.** `core/model.ts` counts calls and tokens per job and model as a run goes. At the end, `week:build` and `content:fetch` write one row to `model_runs` (migration `20261016000000_model_runs`), including a run that stopped part way, since it still spent money: the kind of run, whether it finished, when, the theme, week, days built, how many children it built for, and per job and model the calls, tokens in and out and cost. Counts and money only: no prompts, no card text, and never which child (rule 7). A run is priced when it ends (`runRow()` in `core/runs.ts`), so a later price change doesn't rewrite it. Guardians read the rows through row-level security; only the scripts write them. If the table is missing the script says so and finishes anyway. Runs before 16 Oct weren't recorded; day 1 on 15 Oct cost $0.91.
- **The estimate.** `estimate()` in `core/runs.ts` takes the five most recent finished `week:build` runs and prices ideas per day (they are shared) and cards per child per day, then a seven-day week for the family's children and a month (52 weeks over 12). A one-child rebuild counts toward cards only; a run that stopped counts toward neither. It includes the second asks those runs needed, and the gate per child per day from the builds that ran it (20 Oct 2026; `npm run gate` on its own is a re-check and doesn't count). It leaves out fetching pictures (once per item). The page shows it beside the first guess above ($5.70 a week), says plainly that it is an estimate and what it is based on, and points to Anthropic's console for the real bill. Until a week build is recorded, the page shows only the first guess.

## How the Sunday build is built

Built 20 Oct 2026, phase 3 step 6 (`docs/looks-good-slice.md`; the decisions are in docs/08, "The Sunday cron and the Looks-good page"; report `docs/reports/2026-10-20-looks-good-slice.md`). Proven on `quark-test`; nothing of it is on Vercel yet.

- **Why a day a firing.** A week does not fit one function and a day does. Built a child after a child, a day of week 1 took 195 to 268 seconds, a week would be about 25 minutes, and a Hobby function stops at 300 seconds. So one route builds the next unbuilt day of next week each time it is called, and Vercel calls it eight times.
- **The eight calls.** `vercel.json`: eight entries on `/api/cron/week`, on Sunday, Hawaii time, 6 am, 8 am, 10 am, noon, 2 pm, 4 pm, 6 pm and 8 pm (the UTC expressions `0 16 * * 0` to `0 4 * * 1`, then the spare `0 6 * * 1`; Hawaii has no daylight saving). Hobby fires an entry anywhere within its hour, so the week is ready by 7 pm Sunday and the 8 pm firing is a spare for a day an earlier one lost. A test holds the eight, their Hawaii times and the route's `maxDuration`.
- **The route.** `app/api/cron/week/route.ts`, `GET`, `maxDuration = 300` (accepted beside `cacheComponents`; `next build` puts it in `functions-config-manifest.json`). It compares the `Authorization` header with `Bearer <CRON_SECRET>` by hash and `timingSafeEqual` (`lib/cron-auth.ts`), and answers 401, having read and written nothing, when the header is wrong or `CRON_SECRET` is not set. Off Vercel it answers 403 unless `QUARK_TARGET` is `test`, so a call to localhost cannot reach a live key. Its reply is `{outcome, week, day, theme, reason, cost, seconds}` and never a nickname; it is 200 except `failed`, which is 500 so Vercel's log shows it. It is outside `proxy.ts`'s matcher.
- **Which week and which day.** `nextWeek()` in `core/curation/cron.ts` (pure): next Monday is the Monday after today where the family lives (04:00 UTC on a Monday is still Sunday in Hawaii). A theme the cron made for that Monday is gone on with; any other theme starting then or later is "already built" and left alone, never rebuilt; otherwise the week is the family's highest plan week plus one, however many Sundays were skipped. The cron's own themes are known by a `theme` row it writes the moment a theme is made, so a firing that stops after making one does not strand the week. The day is the earliest one that is not complete: exactly 20 ideas and, for each child, 20 cards and 20 questions. A day that is short, or was written twice (nothing in the database stops that), is cleared and built again. A theme that is `live` or `done` is never touched.
- **Refusals, before anything is spent.** In this order: another firing already working on the day; the week already built; a model name or the API key missing; the library cannot fill the week (`weekSchedule()`'s error, naming the short slots); the gate cannot run (no rulebook, or a saved one older than the guardians' answers). Each ends the firing as a `refused` row. With no family, or two, the refusal is only the reply: `audit_log` needs a family to write to.
- **The record.** One `audit_log` row (`week.cron`, no guardian) when a firing starts, one when it makes a theme, and one when it ends as `built`, `nothing`, `refused` or `failed`, linked by the start row's id. A failure's text goes through `faultText()` and then has every nickname taken out. A firing that spent also writes a `model_runs` row (`week:build`, one day), counted by `/parent/models`; a firing stopped by the time limit writes none, so the page undercounts it.
- **The lock.** Vercel's delivery is best effort: a firing can be missed or delivered twice. Each firing writes its start row, then reads the start rows of the last ten minutes for the same week and day, and only the earliest that has not ended goes on (ties broken on the id); a firing that has ended holds nothing, so a hand retry after a failure is not kept waiting. After taking the lock it reads the day's counts again and builds nothing if another firing built it meanwhile. This is what stands between a duplicate delivery and a doubled day; the real lock would be unique indexes on `ideas` and `cards`, a migration that is a board row (before a real week 2 on live).
- **One-day mode.** `buildWeek` with `day` builds that day into the week's theme: day 1 makes the theme, the earlier days' chains are loaded so each slot carries on from its own, the lenses and doors are planned over all seven days and the day takes its own (a test builds a week out of order, a day at a time, and gets the lenses, doors and levels of one built whole), and the theme stays `generating` until all seven days are in. A day that already has ideas is refused unless `rebuild`, which clears that one day first. `week:build -- --week N --day D [--rebuild]` is the same rule by hand, and the repair for a lost day (on live it is `week:build:live`, a live command at a stop).
- **The gate in a firing.** The cards of the week still pending are checked, and only those (`pendingOnly` in `runGate`): a verdict reached under another rulebook is left to the tap's refusal and to `npm run gate`, so a rulebook changed on Sunday morning cannot make a later firing re-judge, and spend on, the whole week. A firing that finds all seven days built still checks what an earlier firing left pending (nothing, and $0, when nothing is).
- **One copy of the wiring.** `core/curation/week-job.ts` (`prepareWeek`, `buildDays`), `gate-run.ts`, `cron.ts` (pure) and `cron-job.ts` (the database side of a firing) are used by the scripts and the route alike; a test holds that `buildWeek` and `runGate` are reached only through them. Each run counts its own model calls with a meter (`makeMeter()`, `meteredComplete()`), because a warm Vercel instance keeps an earlier firing's counts in the process-wide counter.
- **Hand tools.** `npm run cron:week` fires the route once against the dev server on this laptop (test; it uses `node:http` because `fetch` gives up after five minutes). `npm run fixture` (test only, no live twin) shows a week, sets one passed card back to pending, deletes a week, and reads the audit log and the model runs.
- **How to stop it.** Vercel, the project's Settings, Cron Jobs, Disable Cron Jobs (it stays off through later deploys); or remove `CRON_SECRET` from Vercel's environment, so every firing is a 401. It starts only when Brandon sets `CRON_SECRET`, `ANTHROPIC_API_KEY` and the three model names in Vercel's production environment; until then the release can reach `main` with the cron asleep. Its first Sunday builds week 2 and will refuse for want of lessons (week 1 uses all 28), spending nothing.

**How long a day takes, and the rule (decided 20 Oct 2026).** Measured on `quark-test`, the whole of week 1 through the route:

| Day | Seconds | Cost | Cards and gate |
|---|---|---|---|
| 1 | 209.4 | $1.71 | a child after a child, four at a time; the gate four at a time |
| 2 | 237.0 | $1.86 | the same |
| 3 | 198.6 | $1.71 | the same |
| 4 | 206.2 | $1.79 | the same |
| 5 | 268.5 | $1.88 | the same: over the 240-second line, the stop |
| 6 | 131.4 | $1.85 | both children at once, five calls a child; the gate eight at a time |
| 7 | 125.2 | $1.84 | the same |

The old days ran 195 to 268 seconds, and the time did not follow the number of calls (days 4 and 5 both made 12 card calls and took 206 and 268), so it is the model's latency that moves it. At 125 to 131 seconds a day has about 170 seconds of room under the cap. **The rule: a day under 240 seconds is fine; a day over 240 is the Pro conversation** (Pro stops a function at 800 seconds), and the first thing to look at is whether the latency or the work has grown. The week cost $12.64 through the route (the estimate on `/parent/models` says about $13), inside the $25 run line.

**The rate-limit failure mode.** With ten card calls and eight gate calls in flight, a rate limit is the likeliest way a firing fails. The SDK retries a rate-limited call twice by itself; if it still fails, the firing ends as a `failed` row, the day is left half built, and the next firing clears and rebuilds it (the 8 pm spare covers one lost firing; two lost leave a day missing on Monday, which `/parent` names and the tap refuses). Nothing was rate-limited in the two days built this way, but it has not been provoked.

**Limits, known and left.**
- **A day with pictures is not proved.** `content:fetch` has never run on `quark-test`, so the proof week was text only. A day with pictures adds the offered items to the idea prompt and can send a chain back once for a missing first picture (one more call in parallel); my estimate, not measured, is about 160 seconds. The first Sunday on live is the first such day through the route.
- **The lens plan can drift once phase 4 records taps.** The lenses are planned at each firing from the child's history, which is empty now. When the wall records taps, the boys will tap on Sunday, so a later firing could plan different lenses than an earlier one; the fix then is to keep the week's lens plan from day 1.
- **A firing stopped at the cap writes no run row**, so `/parent/models` undercounts it. A week left `generating` (a lost day) shows on `/parent` as "being built", cannot be tapped, and the cron moves on to the next week; the lost days are built by hand.

## How a week goes live

Built 20 Oct 2026, the same step. Rule 5 and the 13 Oct decision: a week reaches a child only after a guardian has seen it and said it looks good. The Sunday build leaves a week in `review`; the tap makes it `live`.

- **The tap.** `/parent/week/[theme]` opens with the week's state ("Ready for you to read", "Live from Monday 26 October", "Being built: 5 of 7 days") and one button. Any one guardian can press it (rule 2); one is enough. `makeWeekLive()` in `app/parent/week/[theme]/actions.ts` reads everything again on the server and never takes it from the page, and the status moves only by an update that matches a theme still in `review`, so two guardians tapping at once leave one winner and the other is told the week is already live. It writes an audit row (`theme.live`: the theme, the week, the rulebook's hash, the floor's version, the cards passed and held back); if that row cannot be written the status goes back.
- **What refuses it** (`liveProblems()` in `core/curation/live.ts`, pure, tested): a week not in `review`; fewer than seven days built for any child (added in the build, because a trial week would otherwise go live with empty days); any card still pending, or marked passed with no verdict behind it; any verdict reached under a rulebook other than the one the guardians' answers make now, which is the hash of the answers (`currentRulebookHash()`), not the saved rulebook, so a saved one that lags refuses too and the page says to open the rulebook page once; any verdict reached under an older safety floor. It checks the floor's version, not whether the floor is still a first guess: removing the "A first guess, pending June" line is not a new floor version (decided 20 Oct 2026), each verdict records the flag itself, and the page counts the verdicts reached while it was one. The reasons are listed together, and a refusal from the server redraws the page, so a stale tab shows the truth.
- **Taking it back.** Any guardian can take a live week back to review until its first day begins where the family lives (Monday, midnight, Hawaii), with a `theme.review` row. After that, holding back one card is the Wonder Wall's.
- **What a guardian reads first, per child:** what passed, what was held back by the card checks, by their rulebook and by the checker, what is not checked; the day-slots whose first card is missing, by name ("No Look card on Tuesday for…"); the deeper layers held back, counted; the safety floor's version and whether it is still a first guess; and whether every card was checked against the rulebook as it is today. The copy says "checker", "held back" and "your rulebook", never "AI", and when the fix is a command at the laptop it says "whoever runs Quark can check them again". The week is "made live by [guardian] on Sunday at 7:12 pm"; naming the guardian is fine, since the audit log is open to every guardian.
- **`/parent`** says which week is ready to read, and one line on the latest Sunday's build from the audit rows: "Sunday's build: week 2, 7 of 7 days, ready at 6:04 pm, $12.31.", or what refused and that nothing was spent, or which firing did not finish. `/parent/models` says whether the Sunday build is set up (whether `CRON_SECRET` is set, never its value). No email and no notification.
- **What live means today: nothing a child sees,** since the wall is phase 4. It is the first switch the kid view reads, so the rule for phase 4 is written here: **the wall shows a card only when its theme is `live`, the card has `passed`, and its day is today.**
- **The gap this leaves.** A signed-in guardian's session can update `themes` and `cards` directly through Supabase's data API (`20261010000002`), and can insert `audit_log` rows, so the tap's checks can be gone around. No page does it. Closing it is a migration, a board row (phase 4, high), and it lands before any theme is made live on live.
